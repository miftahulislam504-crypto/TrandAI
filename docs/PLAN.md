# Market Research System: বিস্তারিত পরিকল্পনা

বাংলাদেশের ই-কমার্স প্ল্যাটফর্ম (Daraz, Cartup, Rokomari ও অন্যান্য), Google Trends এবং Facebook Ads Library থেকে ডেটা নিয়ে প্রতিটা প্রোডাক্টকে **Best / Mid / Don't** ট্যাগ দেওয়ার সিস্টেম।

---

## ১. লক্ষ্য

**সিস্টেম যে প্রশ্নগুলোর উত্তর দেবে**
- কোন প্রোডাক্টের ডিমান্ড কেমন?
- কোনটা ট্রেন্ডিং, মানে চাহিদা বাড়ছে?
- কোনটার রিভিউ ভালো, খারাপ রিভিউ কম?
- কোনটা সবচেয়ে বেশি বিক্রি হচ্ছে?

**প্রতিটা প্রোডাক্টের আউটপুট**
- ০–১০০ স্কোর
- ট্যাগ: Best / Mid / Don't
- কনফিডেন্স: High / Medium / Low
- ট্যাগের কারণ (২–৩টা লাইন, যেমন "৭ দিনে বিক্রি +৩৮%", "রেটিং ৪.৫ (২১০টি রিভিউ)")

**শুরুতে যা থাকবে না (Non-goals)**
- নিজের স্টোরের সাথে ইন্টিগ্রেশন
- অটো অর্ডার বা অটো প্রাইসিং
- পাবলিক ইউজার অ্যাকাউন্ট

## ২. সিস্টেম আর্কিটেকচার

```
[Daraz] [Cartup] [Rokomari] [অন্যান্য]   [Google Trends]   [FB Ads Library]
    \        |        /                        |                  |
     +------ Source Adapters (প্রতি সোর্সে একটা) ------+
                          |
                   Raw Storage (HTML/JSON)
                          |
          Parse -> Normalize -> Product Matching
                          |
        Daily Snapshots + Reviews + Trend + Ads (Database)
                          |
                  Metrics (দৈনিক হিসাব)
                          |
                   Scoring Engine
                          |
            Scores + Tier + Confidence + Reasons
                          |
                 Dashboard (Next.js)
```

**মূল নীতি**
1. **Adapter প্যাটার্ন:** প্রতিটা সোর্সের জন্য আলাদা adapter, সবগুলো একই ফরম্যাটে ডেটা দেবে। নতুন সাইট যোগ করতে শুধু নতুন adapter লাগবে।
2. **Raw ডেটা সেভ:** HTML/JSON কিছুদিন রাখা হবে। পার্সার ভেঙে গেলে বা লজিক বদলালে আবার স্ক্র্যাপ না করে রি-পার্স করা যাবে।
3. **স্ন্যাপশট, ওভাররাইট নয়:** প্রতিদিনের অবস্থা আলাদা সারিতে জমা হবে। ট্রেন্ড বের হবে এই ইতিহাস থেকে।
4. **স্কোরিং আলাদা স্তর:** স্ক্র্যাপিং আর স্কোরিং আলাদা থাকবে, যাতে ফর্মুলা বদলালে ডেটা নতুন করে সংগ্রহ করতে না হয়।

## ৩. ডেটা সোর্স

| সোর্স | কী সংগ্রহ হবে | পদ্ধতি | ফ্রিকোয়েন্সি | ঝুঁকি |
|---|---|---|---|---|
| **Daraz** | প্রোডাক্ট id, নাম, ব্র্যান্ড, ক্যাটাগরি, দাম, আগের দাম, রেটিং, রেটিং সংখ্যা, রিভিউ টেক্সট/স্টার/তারিখ, সোল্ড কাউন্ট (যেখানে দেখায়), সেলার | সাইটের JSON/XHR endpoint খুঁজে দেখা; না পেলে Playwright | প্রতিদিন | অ্যান্টি-বট, লেআউট বদল |
| **Cartup** | একই ফিল্ড, যতটা দেখায় | সাইট অডিটের পর ঠিক হবে | প্রতিদিন | সোল্ড কাউন্ট নাও থাকতে পারে |
| **Rokomari** | বইয়ের নাম, লেখক, ISBN, দাম, রেটিং, রিভিউ, বেস্টসেলার র‍্যাংক | সাইট অডিটের পর ঠিক হবে | প্রতিদিন | বইয়ে বিক্রির সংখ্যা নাও থাকতে পারে |
| **অন্যান্য BD সাইট** | একই | Phase 4-এ একটা একটা করে | প্রতিদিন | সাইটভেদে আলাদা |
| **Google Trends** | কীওয়ার্ডের সার্চ ইন্টারেস্ট, geo=BD, গত ১২ মাস ও গত ৯০ দিন, related queries | pytrends (আনঅফিসিয়াল) বা সমতুল্য | সাপ্তাহিক | রেট লিমিট, কম ভলিউমে ডেটা না আসা |
| **FB Ads Library** | কীওয়ার্ড বা পেজ ধরে অ্যাক্টিভ বিজ্ঞাপন: পেজের নাম, বিজ্ঞাপন শুরুর তারিখ, কপি, ডেস্টিনেশন URL | ওয়েবসাইট (API নয়) | সাপ্তাহিক | ToS, ব্লক |

**প্রতিটা সোর্সের সীমাবদ্ধতা**
- **Google Trends:** ভ্যালু ০–১০০ রিলেটিভ, আসল সার্চ সংখ্যা নয়। একসাথে সর্বোচ্চ ৫টা কীওয়ার্ড তুলনা করা যায়। ব্যাচ বদলালে স্কেল বদলে যায়, তাই প্রতিটা ব্যাচে একটা **anchor কীওয়ার্ড** রেখে নর্মালাইজ করতে হবে।
- **FB Ads Library:** অফিসিয়াল API ইইউ ও ইউকের বাইরে শুধু রাজনৈতিক ও সামাজিক ইস্যুর বিজ্ঞাপন দেয়। কমার্শিয়াল বিজ্ঞাপন শুধু ওয়েবসাইটে দেখা যায় এবং সেখানে ইম্প্রেশন বা খরচ থাকে না। তাই এটা শুধু "কতজন, কতদিন ধরে বিজ্ঞাপন চালাচ্ছে" সিগন্যাল হিসেবে ব্যবহার হবে।
- **সোল্ড কাউন্ট:** প্রতিটা সাইটে এটা আছে কি না এবং কীভাবে দেখায় (রাউন্ড করা, মোট না মাসিক) Phase 0-তে যাচাই করতে হবে।

**প্রোডাক্ট ডিসকভারি (কোন প্রোডাক্ট ট্র্যাক হবে)**
- প্রতিটা ক্যাটাগরির বেস্টসেলার, পপুলার ও নতুন তালিকা থেকে শীর্ষ N টা (শুরুতে ২০০–৫০০) ধরা হবে।
- সাথে কীওয়ার্ড সার্চের ফলাফল।
- নতুন প্রোডাক্ট তালিকায় এলে স্বয়ংক্রিয়ভাবে ট্র্যাকিংয়ে যোগ হবে। ৩০ দিন তালিকার বাইরে থাকলে নিষ্ক্রিয় হবে।

## ৪. ডেটা মডেল (PostgreSQL)

```sql
create table sources (
  id serial primary key,
  name text unique not null,           -- daraz, cartup, rokomari
  base_url text,
  has_sold_count boolean default false,
  is_active boolean default true
);

create table categories (
  id serial primary key,
  name text not null,
  parent_id int references categories(id)
);

create table canonical_products (
  id bigserial primary key,
  name text not null,
  brand text,
  model text,
  isbn text,                           -- বইয়ের জন্য
  category_id int references categories(id),
  created_at timestamptz default now()
);

create table listings (
  id bigserial primary key,
  source_id int references sources(id),
  external_id text not null,           -- প্ল্যাটফর্মের নিজস্ব product id
  url text not null,
  title_raw text,
  brand_raw text,
  seller_name text,
  category_id int references categories(id),
  canonical_product_id bigint references canonical_products(id),
  match_confidence numeric,
  first_seen_at timestamptz default now(),
  last_seen_at timestamptz,
  is_active boolean default true,
  unique (source_id, external_id)
);

create table listing_snapshots (
  listing_id bigint references listings(id),
  captured_on date not null,
  price numeric,
  original_price numeric,
  rating_avg numeric,
  rating_count int,
  review_count int,
  sold_count int,                      -- null মানে সোর্সে নেই
  in_stock boolean,
  primary key (listing_id, captured_on)
);

create table reviews (
  id bigserial primary key,
  listing_id bigint references listings(id),
  external_review_id text,
  stars smallint,
  body text,
  lang text,                           -- bn, en, banglish
  reviewed_at date,
  reviewer_hash text,                  -- নাম নয়, হ্যাশ
  suspected_fake boolean default false,
  sentiment smallint,                  -- -1, 0, 1
  topics text[],
  unique (listing_id, external_review_id)
);

create table trend_keywords (
  id serial primary key,
  keyword text not null,
  geo text default 'BD',
  canonical_product_id bigint references canonical_products(id),
  category_id int references categories(id)
);

create table trend_points (
  keyword_id int references trend_keywords(id),
  week_start date,
  value numeric,                       -- anchor দিয়ে নর্মালাইজড
  primary key (keyword_id, week_start)
);

create table ad_observations (
  id bigserial primary key,
  canonical_product_id bigint references canonical_products(id),
  keyword text,
  page_name text,
  ad_library_id text,
  ad_start_date date,
  destination_url text,
  observed_on date,
  is_active boolean,
  unique (ad_library_id, observed_on)
);

create table product_scores (
  canonical_product_id bigint references canonical_products(id),
  scored_on date,
  demand numeric,
  trend numeric,
  review_quality numeric,
  bad_review numeric,
  ads_signal numeric,
  total numeric,
  tier text check (tier in ('best','mid','dont')),
  confidence text check (confidence in ('high','medium','low')),
  reasons jsonb,
  primary key (canonical_product_id, scored_on)
);

create table scrape_runs (
  id bigserial primary key,
  source_id int references sources(id),
  started_at timestamptz,
  finished_at timestamptz,
  status text,                         -- ok, partial, failed
  items_ok int,
  items_failed int,
  error text
);
```

**নোট**
- Phase 1–3-এ শুধু Daraz থাকলে প্রতিটা listing-এর জন্য একটা করে `canonical_product` স্বয়ংক্রিয় তৈরি হবে (১:১)। Phase 4-এ ম্যাচিং এসে এগুলো মার্জ করবে।
- `listing_snapshots`-এ প্রতিদিন প্রতি প্রোডাক্টে একটা সারি। ৫০০ প্রোডাক্ট × ৩৬৫ দিন × কয়েকটা সোর্সেও ডেটা ছোটই থাকবে। রিভিউ টেবিল সবচেয়ে দ্রুত বাড়বে।

## ৫. স্ক্র্যাপিং ও ইনজেশন পরিকল্পনা

**Adapter ইন্টারফেস (প্রতি সোর্সে একই)**
```
discover_products(category) -> [listing_ref]
fetch_product(listing_ref)  -> {price, rating, sold, ...}
fetch_reviews(listing_ref, since_date) -> [review]
```

**ভদ্র স্ক্র্যাপিং নিয়ম**
- রিকোয়েস্টের মাঝে ২–৫ সেকেন্ড র‍্যান্ডম বিরতি।
- robots.txt ও সাইটের ToS আগে পড়া। সোর্সভেদে সিদ্ধান্ত নেওয়া।
- ব্যর্থ হলে exponential backoff (সর্বোচ্চ ৩ বার), তারপর স্কিপ ও লগ।
- রিভিউ ইনক্রিমেন্টাল: শেষ স্ক্র্যাপের পরের নতুন রিভিউ আনা হবে, প্রতিবার সব নয়।
- ব্যক্তিগত তথ্য (রিভিউয়ারের নাম, ছবি) সেভ হবে না, শুধু হ্যাশ।

**রান ও মনিটরিং**
- প্রতিটা রান `scrape_runs`-এ লগ হবে।
- কোনো সোর্সে সফলতার হার ৮০%-এর নিচে নামলে অ্যালার্ট (Telegram বা ইমেইল)। সাধারণত এর মানে সাইটের লেআউট বদলেছে।
- প্রতিটা adapter-এর জন্য ছোট টেস্ট ফিক্সচার (সেভ করা HTML) থাকবে।

**শিডিউলিং**
- প্রধান অপশন: GitHub Actions cron, প্রতিদিন রাতে। সার্ভার লাগে না।
- সীমাবদ্ধতা: ফ্রি মিনিটের সীমা, জবের সময়সীমা, এবং কিছু সাইট GitHub-এর IP ব্লক করতে পারে।
- বিকল্প: Render cron job বা ছোট VPS, যদি Actions-এ ব্লক হয়।

## ৬. প্রোডাক্ট ম্যাচিং

একই প্রোডাক্ট Daraz ও Cartup-এ আলাদা নামে থাকে। তাই কয়েক স্তরে মেলানো হবে:

1. **নিশ্চিত ম্যাচ:** বইয়ে ISBN, অন্য প্রোডাক্টে ব্র্যান্ড + মডেল নম্বর একই হলে সরাসরি মার্জ।
2. **ফাজি ম্যাচ:** নাম নর্মালাইজ (ছোট হাতের অক্ষর, বিশেষ চিহ্ন বাদ, বাংলা ↔ ইংরেজি ট্রান্সলিটারেশন), ব্র্যান্ড অভিধান, দামের পার্থক্য ±৩০%, rapidfuzz দিয়ে মিল স্কোর।
3. **রিভিউ কিউ:** মিল স্কোর ০.৭–০.৮৫ হলে অ্যাডমিন ড্যাশবোর্ডে "হ্যাঁ/না" ক্লিকের জন্য জমা হবে।
4. **ক্যাশ:** কনফার্ম করা ম্যাচ সংরক্ষিত থাকবে, আবার হিসাব হবে না।

**একই সোর্সে একই প্রোডাক্টের একাধিক সেলার**
- একই `canonical_product`-এর নিচে একাধিক listing। বিক্রি ও রিভিউ যোগ হবে, দামের পরিসীমা (min/max) আলাদা মেট্রিক হবে।

**Google Trends কীওয়ার্ড ম্যাপিং**
- প্রতিটা প্রোডাক্ট বা ক্যাটাগরির জন্য ১–৩টা কীওয়ার্ড (ইংরেজি + বাংলা)। ব্র্যান্ড + মডেল থেকে স্বয়ংক্রিয় প্রস্তাব, শীর্ষ প্রোডাক্টে হাতে যাচাই।
- কম সার্চ ভলিউমের প্রোডাক্টে Trends কিছু দেয় না। তখন ক্যাটাগরি-লেভেল কীওয়ার্ড ব্যবহার হবে এবং কনফিডেন্স কমবে।

## ৭. স্কোরিং সিস্টেম

### ৭.১ সাধারণ নিয়ম
- সব তুলনা **ক্যাটাগরির ভেতরে** (percentile)। বইয়ের সাথে ইলেকট্রনিক্স মেলানো হবে না।
- প্রতিটা ফ্যাক্টর ০–১০০ স্কেলে।
- ওজন কনফিগ ফাইলে থাকবে, কোড বদলাতে হবে না।

### ৭.২ ফ্যাক্টর ও শুরুর ওজন

| ফ্যাক্টর | ওজন | কী মাপে |
|---|---|---|
| Demand | 30% | বিক্রির পরিমাণ |
| Trend | 25% | চাহিদা বাড়ছে কি কমছে |
| Review Quality | 20% | সংখ্যা-সংশোধিত রেটিং |
| Bad Review | 15% | খারাপ রিভিউয়ের অনুপাত ও ধরন |
| Ads Signal | 10% | বিজ্ঞাপনে বাজার-সমর্থন |

### ৭.৩ প্রতিটা ফ্যাক্টরের হিসাব

**Demand (30%)**
- মোট সোল্ডের চেয়ে **সাম্প্রতিক বিক্রির গতি** বেশি গুরুত্বপূর্ণ।
- হিসাব: ৭০% ক্যাটাগরির ভেতরে ৩০ দিনের বিক্রির পার্থক্যের (Δsold) percentile + ৩০% মোট সোল্ডের percentile।
- সোল্ড কাউন্ট না থাকলে রিভিউ সংখ্যার বৃদ্ধি (Δreview_count) প্রক্সি হিসেবে নেওয়া হবে এবং কনফিডেন্স কমবে।
- একাধিক প্ল্যাটফর্মে মিলে গেলে বিক্রি যোগ হবে।

**Trend (25%)**
- **বিক্রির গতি বদল:** গত ৭ দিন বনাম আগের ৭ দিন।
- **Google Trends:** গত ৪ সপ্তাহের গড় বনাম আগের ৮ সপ্তাহের গড়, সাথে ১২ মাসের গড়ের তুলনায় বর্তমান অবস্থান।
- দুটোই থাকলে ৫০/৫০, একটা থাকলে সেটাই।
- **সিজনালিটি:** ঈদ, রমজান, পহেলা বৈশাখ, শীত/বর্ষার মতো মৌসুমে ভুল ট্রেন্ড ধরা পড়ে। এক বছরের বেশি ডেটা জমলে গত বছরের একই সময়ের সাথে তুলনা (YoY) যোগ হবে। তার আগে সিজনাল কীওয়ার্ডে "Seasonal" ফ্ল্যাগ থাকবে।

**Review Quality (20%)**
- Bayesian average:

```
adjusted = (v / (v + m)) * R + (m / (v + m)) * C
v = রেটিং সংখ্যা, R = প্রোডাক্টের গড়, C = ক্যাটাগরির গড়, m = 30 (শুরুতে)
```

- উদাহরণ (C = 4.2, m = 30):
  - ২টা রিভিউয়ে ৫.০ → adjusted ≈ **4.25**
  - ৩,০০০ রিভিউয়ে ৪.৭ → adjusted ≈ **4.70**
- গত ৯০ দিনের রিভিউয়ের ওজন বেশি, যাতে পুরনো ভালো রেটিং ধরে না রাখে।
- সন্দেহজনক ভুয়া রিভিউ বাদ বা কম ওজনে।
- adjusted রেটিং ১–৫ থেকে ০–১০০-তে রূপান্তর।

**Bad Review (15%)**
- ১–২ স্টার রিভিউয়ের স্মুথড অনুপাত: `(bad + a) / (n + a + b)`।
- টেক্সট থেকে খারাপ ধরনের ট্যাগ: নকল/ফেক, ছবির মতো না, ডেলিভারি দেরি, ভাঙা/ত্রুটিপূর্ণ।
- "নকল/ফেক" অভিযোগের অনুপাত বেশি হলে **রেড ফ্ল্যাগ**: প্রোডাক্ট Best হতে পারবে না।

**Ads Signal (10%)**
- যে বিজ্ঞাপনদাতারা প্রোডাক্টের বিজ্ঞাপন চালাচ্ছে তাদের সংখ্যা (একটা সীমা পর্যন্ত)।
- সবচেয়ে দীর্ঘ চলা বিজ্ঞাপনের দিন: ৩০+ দিন মানে বিজ্ঞাপনদাতার কাছে প্রোডাক্ট লাভজনক হওয়ার ইঙ্গিত।
- নতুন বিজ্ঞাপনের বৃদ্ধির হার।
- বিজ্ঞাপনদাতা বেশি মানে প্রতিযোগিতাও বেশি। তাই এটা আলাদা **Competition ব্যাজ** হিসেবেও দেখানো হবে।

### ৭.৪ ডেটা না থাকলে
- যে ফ্যাক্টরের ডেটা নেই সেটা বাদ দিয়ে বাকিগুলোর ওজন আবার ১০০%-এ ভাগ হবে।
- কনফিডেন্স নির্ভর করবে: কতগুলো ফ্যাক্টর আছে, রিভিউ সংখ্যা, কত দিনের ইতিহাস, কয়টা সোর্সে আছে।
- ইতিহাস ১৪ দিনের কম হলে বিক্রির গতি ধরা হবে না, ট্রেন্ড শুধু Google Trends থেকে।

### ৭.৫ ট্যাগ নির্ধারণ

| ট্যাগ | শর্ত |
|---|---|
| **Best** | স্কোর ≥ 75 এবং নিচের সব গেট পাস |
| **Mid** | স্কোর 45–75 |
| **Don't** | স্কোর < 45 অথবা Don't ট্রিগার |

**Best-এর গেট (শুরুর মান, কনফিগে বদলানো যাবে)**
- রেটিং সংখ্যা ≥ 20
- adjusted রেটিং ≥ 4.0
- খারাপ রিভিউ ≤ 10%
- Demand percentile ≥ 60
- কনফিডেন্স ≥ Medium (Low কনফিডেন্সে "Best (Provisional)" দেখাবে)
- ফেক/নকল রেড ফ্ল্যাগ নেই

**Don't ট্রিগার**
- adjusted রেটিং < 3.3
- খারাপ রিভিউ ≥ 25%
- টানা ৪ সপ্তাহ বিক্রি ও ট্রেন্ড দুটোই কমছে
- নকল/ফেক অভিযোগ অনেক

**স্থিতিশীলতা:** স্কোর থ্রেশহোল্ডের ±3 এর মধ্যে ঘুরলে ট্যাগ বারবার বদলাবে। তাই ট্যাগ বদলাতে হলে টানা ৩ দিন নতুন অবস্থানে থাকতে হবে।

**ক্যালিব্রেশন:** শুরুর থ্রেশহোল্ড অনুমান। Phase 2-এ আসল ডেটা এলে স্কোরের বণ্টন দেখে ঠিক করা হবে। বিকল্প: ক্যাটাগরির শীর্ষ ১৫% = Best, নিচের ২৫% = Don't।

### ৭.৬ ব্যাখ্যা (Reasons)
প্রতিটা প্রোডাক্টে সবচেয়ে বেশি প্রভাব ফেলা ২–৩টা কারণ `reasons` ফিল্ডে JSON হিসেবে সেভ হবে। ড্যাশবোর্ডে ট্যাগের পাশে দেখাবে।

## ৮. রিভিউ বিশ্লেষণ

**ভাষা:** বাংলা, ইংরেজি, Banglish (ইংরেজি হরফে বাংলা)। ভাষা শনাক্ত করে আলাদা প্রসেসিং।

**সেন্টিমেন্ট ও টপিক**
- শুরুতে স্টার + কীওয়ার্ড তালিকা (নকল, ভাঙা, দেরি, ভালো মান, প্যাকেজিং ইত্যাদি)।
- পরে LLM (Claude API) দিয়ে ব্যাচে টপিক ও সেন্টিমেন্ট: মান, ডেলিভারি, অরিজিনালিটি, সাইজ, প্যাকেজিং, দাম।
- খরচ কমাতে শুধু নতুন রিভিউ প্রসেস হবে, ব্যাচ করে।

**ভুয়া রিভিউ শনাক্তকরণ (হিউরিস্টিক)**
- অল্প সময়ে অনেক ৫ স্টারের হঠাৎ ঢেউ
- হুবহু বা প্রায় একই টেক্সট
- খুব ছোট ও জেনেরিক টেক্সটের উচ্চ অনুপাত ("good", "nice product")
- সোল্ড কাউন্টের তুলনায় রিভিউ সংখ্যা অস্বাভাবিক বেশি
- রেটিং বণ্টন U-আকৃতির (শুধু ১ আর ৫ স্টার)
- ফলাফল: `suspected_fake` ফ্ল্যাগ। রেটিং হিসাবে এই রিভিউ বাদ বা কম ওজনে।

## ১১. ফেজ পরিকল্পনা

প্রতিটা ফেজ শেষে ZIP বা শুধু বদলানো ফাইল দেওয়া হবে, যাতে একটা একটা করে পুশ ও টেস্ট করা যায়।

### Phase 0: সোর্স অডিট (আকার: ছোট)
- প্রতিটা সাইট হাতে দেখে ফিল্ডের তালিকা: সোল্ড কাউন্ট আছে কি, রিভিউ কীভাবে লোড হয়, বট প্রোটেকশন কেমন।
- robots.txt ও ToS পড়া।
- প্রথম ক্যাটাগরি ঠিক করা।
- ২–৩টা প্রোডাক্টে হাতে স্কোর হিসাব করে ফর্মুলা পরীক্ষা।
- **ডেলিভারেবল:** সোর্স অডিট টেবিল।

### Phase 1: Daraz MVP (আকার: বড়)
- ডাটাবেজ স্কিমা, Daraz adapter (ডিসকভারি + প্রোডাক্ট + রিভিউ), দৈনিক cron।
- সাধারণ ড্যাশবোর্ড: প্রোডাক্ট তালিকা ও ডিটেইল (এখনও ট্যাগ নেই)।
- **সম্পন্ন হবে যখন:** টানা ৭ দিন স্ন্যাপশট জমেছে এবং ট্র্যাক করা প্রোডাক্টের ≥ ৯৫% সফল।

### Phase 2: স্কোরিং v1, শুধু Daraz (আকার: মাঝারি)
- Bayesian রেটিং, খারাপ রিভিউ অনুপাত, বিক্রির গতি, ট্যাগ, কনফিডেন্স, ব্যাখ্যা।
- ড্যাশবোর্ডে Best/Mid/Don't।
- **সম্পন্ন হবে যখন:** ৩০টা প্রোডাক্ট আপনি নিজে যাচাই করে ≥ ৮০% ক্ষেত্রে ট্যাগের সাথে একমত।

### Phase 3: Google Trends (আকার: মাঝারি)
- কীওয়ার্ড ম্যাপিং, anchor নর্মালাইজেশন, Trend ফ্যাক্টর স্কোরে যোগ।
- সিজনাল ফ্ল্যাগ।

### Phase 4: Cartup, Rokomari ও অন্যান্য সাইট + ম্যাচিং (আকার: বড়)
- প্রতিটা সাইটের adapter একটা একটা করে।
- প্রোডাক্ট ম্যাচিং ও রিভিউ কিউ।
- প্ল্যাটফর্ম মিলিয়ে বিক্রি ও দাম।

### Phase 5: রিভিউ ইন্টেলিজেন্স (আকার: মাঝারি)
- ভুয়া রিভিউ ফিল্টার, সেন্টিমেন্ট ও টপিক, রেড ফ্ল্যাগ।

### Phase 6: Ads Library সিগন্যাল (আকার: মাঝারি)

## ১৩. যাচাই ও ক্যালিব্রেশন

- **স্পট চেক:** প্রতিটা ফেজ শেষে আপনি নিজে ২০–৩০টা প্রোডাক্ট দেখে ট্যাগের সাথে একমত কি না জানাবেন।
- **ব্যাকটেস্ট:** ৩০–৬০ দিন পর দেখা হবে, Best ট্যাগ পাওয়া প্রোডাক্টের বিক্রি সত্যিই টিকেছে বা বেড়েছে কি না।
- **স্থিতিশীলতা:** ট্যাগ কত ঘন ঘন বদলাচ্ছে (flip rate) মাপা হবে।
- **বাস্তব ফলাফল:** আপনি নিজে কোনো প্রোডাক্ট বিক্রি করলে আসল বিক্রির সাথে স্কোর মিলিয়ে ওজন ঠিক করা হবে।

## ১৪. যেসব সিদ্ধান্ত দরকার

1. **প্রথম ক্যাটাগরি কোনটা?** (যেমন ফ্যাশন, ইলেকট্রনিক্স, বই, হোম/কিচেন)
